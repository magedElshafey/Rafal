## Root cause and measured space budget

`Header` places the logo, `PrimaryNavigation`, and `HeaderActions` in a flex row
with two minimum 16px gaps. Logo/actions are `shrink-0`; navigation can shrink.
`Container` leaves 720px of content width at a 768px viewport (24px side gutters).
The logo measures 53.06px. Navigation links retain 14px padding on each side.
Five navigation items formerly added four 20px gaps. When width runs out, the
multiword About label wraps while the single-word labels constrain shrinking.
The Arabic authenticated row also intruded 3.53px into its container gutter.

| --- | ---: | ---: |
| Unwrapped navigation, category link fallback, before | 461.38px | 452.80px |
| Anonymous actions | 154.19px | 98.30px |
| Authenticated actions: four 44px targets + three 8px gaps | 200px | 200px |

| Available | 720px | 720px |

A populated category trigger adds another **24px** (chevron + internal gap).
This also reproduced Arabic **anonymous** wrapping at 768/769px with current
public categories, although the empty-category fixture does not reproduce it.

The 4px tablet gap recovers **64px**. Even reserving the full authenticated
200px action width with a populated menu leaves 13.56px spare in Arabic and
22.14px in English at 768px. This extra case was checked by temporarily reserving
that width in the anonymous browser document; it is a geometry stress check,
not an authenticated populated-category integration test.

## Choice and alternatives

- **Chosen:** `gap-1 lg:gap-5`. Uses the existing 4px spacing grid and `lg`
  breakpoint. Only visible navigation between 768 and 1023px changes. Existing
  mobile navigation remains below `md`; desktop spacing returns at 1024px.
- **8px gaps alone:** save only 48px; Arabic authenticated + populated category
  requires about 50.44px extra. Testing only the empty fixture would miss this.
- **No-wrap/shrink prevention alone:** does not create the missing width and can
  push actions out of bounds. Not added.
- **Reduce link padding, action targets or font size:** unnecessary; all stay intact.
- **Move the mobile breakpoint or hide actions:** would change navigation
  composition and its existing 48rem focus-transfer behavior. Not needed.

No new arbitrary values, client boundaries, state, markup or accessibility
attributes. `git diff --check` passed. All 42 screenshot comparisons outside the
tablet interval have identical header pixels before/after (mobile 64px-high
header; desktop 80px-high header).

### Diagnostic limitations and failures retained

The initial interaction probe marked 18 mobile rows FAIL because it assumed every
Tab stays inside the native dialog DOM. Chromium also tabs into browser chrome:
`document.hasFocus()` becomes false and `activeElement` is BODY. The focused probe
confirmed no background control receives focus. A separate mobile rerun checks
that distinction and retains the original failed diagnostic rows:
[initial](evidence/phase-2b-batch-01-2026-10-27/interactions-initial.json),
[mobile rerun](evidence/phase-2b-batch-01-2026-10-27/interactions-mobile.json).
No repository test assertion was changed.

An open desktop category panel can lose focus to BODY when narrowed from 768 to
767px. [Isolated comparison](evidence/phase-2b-batch-01-2026-10-27/resize.json)
reproduced it with the original 20px gap in both locales and the new spacing in
English; Arabic passed with the new spacing in that sample. The original-spacing
comparison used a browser-only CSS override, not an application-source revert.
Normal mobile→desktop transfers and transitions across `lg` passed. A repeated
English sequence passed, confirming intermittent behavior; earlier timeout
results remain in `extra*.json`. Source inspection finds the existing resize
handler conditionally restores focus only while focus remains within its root;
browser hiding/blur timing is a plausible explanation, **not a proven root cause**.
No state/event-handler changes are authorized in this batch, so this remains
an explicitly outstanding navigation accessibility issue.

Diagnostic script process exit 0 means the script completed; per-row PASS/FAIL
is authoritative. It does not convert these recorded failures into passes.
