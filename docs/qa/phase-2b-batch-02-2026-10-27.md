## Confirmed cause

The desktop navigation is `hidden md:block`. Its category disclosure remains
mounted when the viewport crosses 48rem; CSS hides its ancestor. The existing
media-query callback restores focus only if the menu root still contains
`document.activeElement`. Its effect exists only while the menu is open.

Instrumented browser evidence records this failing sequence:

1. At 768px, a category button inside the open desktop panel owns focus.
2. At 767px, CSS hides the ancestor. The focused button remains connected but is
   no longer visible. Chromium emits `blur`, then `focusout`, with
   `relatedTarget=null`. `document.activeElement` is already BODY and
   **`document.hasFocus()` remains true**.
3. React's root `onBlur` calls `setOpen(false)`. Effect cleanup removes the
   media-query listener before that listener runs. The panel becomes inert and
   `aria-hidden`, and the trigger's expanded state becomes false.
4. The subsequent resize event and two animation frames leave focus on BODY.
   No mobile-trigger focus call occurred.

Other iterations deliver the media-query callback first; its existing transfer
works. This event-order difference explains the intermittency. This is **CSS
hiding and blur/effect cleanup**, not a component unmount, a route change, or
browser-chrome focus. Before editing, **8/40 attempts failed**: Arabic 3/20,
English 5/20, across reduced/normal motion samples.

The browser instrumentation wraps native focus and media-listener methods while
preserving their calls, and records focus/blur events and DOM mutations. It can
affect timing, so the full regression also runs **without instrumentation**.
Evidence: [event sequence CSV](evidence/phase-2b-batch-02-2026-10-27/event-sequence.csv),
[complete paired events](evidence/phase-2b-batch-02-2026-10-27/event-sequence.json),
[all before traces](evidence/phase-2b-batch-02-2026-10-27/before-traces.json).

## Minimal solution

The blur handler still ignores movement within the disclosure and closes on
external blur. Before closing, it restores the existing
`mobile-categories-trigger` **only if all three conditions hold**:

- There is no `relatedTarget` receiving focus.
- The document still has browser focus.
- The existing `(min-width: 48rem)` media query no longer matches.

This handles the CSS-induced blur while the event still identifies the originating
menu, even though `activeElement` has already become BODY. When the media listener
runs first, its existing logic remains effective; blur then has the real mobile
target and does not perform another transfer.

The existing explicit trigger ID is reused. No new selectors, timers, polling,
global listeners, focus-history state, dependencies or breakpoint values.
`document.hasFocus()` prevents treating browser-chrome transitions as a reason
to take focus. Movement to an actual external control is left alone.

Alternatives considered:

- **Delay or poll:** would mask ordering, add latency, and remain timing-dependent.
- **Unconditionally focus in the media callback:** cannot repair a callback
  removed before delivery and could steal unrelated focus.
- **Persistent listener / last-focused-element bookkeeping:** larger lifecycle
  and state changes; unnecessary because the originating blur event is available.
- **Change hiding CSS or restructure menus:** changes visual/interaction design
  without addressing the lifecycle directly.

The native mobile dialog and its background isolation are unchanged. These
navigation components do not use Radix; shared Radix code and attributes were
not touched. Existing Escape handlers, focus-visible classes, category hierarchy,
links and pathname behavior remain unchanged.
